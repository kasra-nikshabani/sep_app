# ADR-0012: ماژول Shop (فروشگاه اینترنتی)

- **وضعیت:** پذیرفته‌شده (Phase 10)
- **تصمیم‌گیرندگان:** Architect + کارفرما (دو فرک واقعی از طریق AskUserQuestion قبل از شروع پیاده‌سازی تأیید شدند)

## Context

طبق بند ۱۵ بریف، Shop باید شامل Products/Categories/Variants/Inventory/Cart/Orders/Payments/Discounts/Coupons/Shipping/Returns باشد. طبق تصمیم قبلی کارفرما در [ADR-0002](0002-modular-monolith-and-module-boundaries.md)، `sepahan-shop` (پروتوتایپ Next.js/Prisma/SQLite موجود) فقط مرجع UI/UX است -- بک‌اند این فاز کاملاً از صفر ساخته می‌شود، بدون هیچ وابستگی به آن.

قبل از شروع پیاده‌سازی، دو فرک معماری واقعی که نمی‌شد بدون تصمیم کارفرما حدس زد از طریق AskUserQuestion مطرح شد:

1. **Shipping**: هیچ شرکت باربری/پستی مشخصی در بریف یا Discovery نیامده بود -- طبق بند ۸ بریف نباید API خارجی حدس زده شود. کارفرما **«فقط داخلی + Placeholder»** را انتخاب کرد.
2. **Returns**: طبق [ADR-0011](0011-payment-architecture.md) Zibal اصلاً API عمومی Refund ندارد و ماژول Wallet هم هنوز ساخته نشده. کارفرما **«فقط گردش‌کار درخواست/تأیید (بدون جابه‌جایی مالی خودکار)»** را انتخاب کرد.

## Decision

### 1) هر Product حداقل یک Variant دارد

حتی محصولات بدون گزینه‌ی واقعی (رنگ/سایز) یک Variant «استاندارد» پیش‌فرض می‌گیرند. این یعنی Cart/Order/Inventory همیشه فقط با `ProductVariant` کار می‌کنند -- نه دو مسیر کد جدا برای محصول ساده/دارای Variant.

### 2) کاهش اتمی موجودی در دیتابیس، نه قفل Redis

برخلاف صندلی تئاتر (ADR-0010) که یک منبع **منحصربه‌فرد** است (یا آزاد یا رزرو، هیچ حالت سومی نیست)، موجودی فروشگاه یک **Pool تعداد** است. یک `UPDATE ... SET stock_quantity = stock_quantity - :qty WHERE stock_quantity >= :qty` اتمی در همان دیتابیس، بدون هیچ Redis، این تضمین را کامل می‌دهد: دو خرید هم‌زمان روی آخرین واحد موجودی هرگز هر دو موفق نمی‌شوند (تست شده با ۲۰ Thread واقعاً هم‌زمان -- `OrderServiceTest.concurrentCheckouts_onLastUnitOfStock_onlyOneSucceeds`).

موجودی در **لحظه‌ی ساخت سفارش** کم می‌شود (نه در لحظه‌ی پرداخت) -- دقیقاً هم‌الگوی `held` شدن صندلی در `reserveSeat`؛ اگر پرداخت تکمیل نشود، Job دوره‌ای (`releaseExpiredOrders`) موجودی را برمی‌گرداند، هم‌خانواده‌ی `releaseExpiredReservations`.

### 3) جداسازی Order/Payment با Event -- بدون تغییر در ماژول Payments

طبق پیش‌بینی ADR-0011، افزودن `purpose=shop_order` نیازی به تغییر منطق `PaymentService` نداشت -- فقط یک Enum جدید و یک Listener جدید (`OrderPaymentListener`، دقیقاً هم‌الگوی `TicketIssuanceListener`) که `PaymentSucceededEvent` را می‌شنود و `OrderService.markOrderPaid` را صدا می‌زند (با `Propagation.REQUIRES_NEW`، همان دلیل باگ واقعی کشف‌شده در Phase 9).

**نکته‌ی عملیاتی واقعی که در همین فاز کشف شد:** ستون `purpose` در `payments.payment` یک `CHECK` Constraint دیتابیسی دارد که مقادیر مجاز را صریح فهرست می‌کند (`ticket_purchase`, `wallet_topup`). افزودن مقدار Enum جدید در کد Java به‌تنهایی کافی نبود -- بدون یک Migration جدید (`V6__add_shop_order_payment_purpose.sql`) که این Constraint را جایگزین کند، اولین تلاش برای ساخت Payment با `purpose=shop_order` با یک خطای واقعی دیتابیسی شکست می‌خورد (کشف‌شده حین اجرای تست، نه یک ریسک نظری).

### 4) حالت لبه‌ای واقعی: پرداخت دیرهنگام بعد از انقضای سفارش

اگر سفارش به‌خاطر گذشتن TTL منقضی و موجودی‌اش آزاد شود، ولی درگاه دیرتر Callback موفق برگرداند (مثلاً کاربر صفحه‌ی پرداخت را دیر بسته)، `markOrderPaid` هرگز خودکار سفارش را `paid` نمی‌کند -- چون پول واقعی گرفته شده اما دیگر هیچ تضمینی برای موجودی وجود ندارد. در عوض `requires_manual_review = true` روی سفارش ست می‌شود تا ادمین دستی بررسی کند (بازپرداخت دستی یا تأمین مجدد کالا). این دقیقاً همان انضباط ADR-0011 است: هرگز فرض خوش‌بینانه در مسیر پول واقعی گرفته نمی‌شود.

### 5) Cart ماندگار و مختص کاربر، بدون Soft-delete/Audit

`shop.cart`/`shop.cart_item` عمداً بدون ستون‌های پایه‌ی `docs/database/conventions.md` (مثل `ticketing.reservation`) -- داده‌ی گذرا و دائم در حال تغییر است.

### 6) کد تخفیف: قفل بدبینانه روی ردیف Coupon حین اعتبارسنجی

`maxUsesTotal`/`maxUsesPerUser` با `SELECT ... FOR UPDATE` (`CouponRepository.findByCodeForUpdate`) چک می‌شوند تا دو خرید هم‌زمان با یک کد محدود هر دو از سقف رد نشوند. سربار این قفل قابل‌قبول است چون فقط یک ردیف (نه یک Table Lock) و فقط طول همان Transaction ساخت سفارش است.

مصرف کد تخفیف (`coupon_redemption`) در لحظه‌ی ساخت سفارش ثبت می‌شود و با لغو/انقضای سفارش برگردانده **نمی‌شود** -- تصمیم عمداً محافظه‌کارانه برای جلوگیری از دور زدن سقف تعداد استفاده با ساخت/رهاسازی مکرر سفارش.

### 7) Shipping: Provider Interface با فقط یک پیاده‌سازی داخلی

`ShippingProvider` (هم‌الگوی `PaymentProvider`، ADR-0005) با یک متد اصلی `calculateCost` و یک Placeholder صریح (`dispatch`) که `UnsupportedOperationException` می‌دهد. هزینه = `baseRate + perKgRate × وزن(kg)` -- یک فرمول واحد Configurable برای هم نرخ ثابت (`perKgRate=0`) و هم نرخ بر اساس وزن، به‌جای دو مسیر کد جدا. **بدون اتصال واقعی به هیچ شرکت باربری/پستی** -- طبق تصمیم صریح کارفرما. اضافه‌کردن یک Provider واقعی در آینده فقط نیازمند یک پیاده‌سازی جدید همین Interface است.

### 8) Returns: فقط گردش‌کار، بدون تسویه‌ی مالی خودکار

`ReturnRequest` یک ماشین‌حالت ساده دارد: `requested → approved/rejected → completed`. `reject` وضعیت سفارش را به مقدار قبل از درخواست مرجوعی برمی‌گرداند (`order_status_before_return`). **هیچ Refund/کیف‌پولی خودکار اجرا نمی‌شود** -- طبق تصمیم صریح کارفرما، چون Zibal رفاند عمومی ندارد (ADR-0011) و Wallet هنوز ساخته نشده. تسویه‌ی مالی واقعی فعلاً کاملاً دستی/خارج از اپ توسط ادمین انجام می‌شود.

## Alternatives Considered

| گزینه | چرا رد شد |
|---|---|
| قفل Redis برای موجودی (هم‌الگوی صندلی تئاتر) | موجودی یک Pool تعداد است، نه یک منبع منحصربه‌فرد -- یک UPDATE اتمی دیتابیسی همان تضمین را بدون وابستگی اضافه به Redis می‌دهد |
| حدس‌زدن یک API واقعی شرکت باربری/پستی برای Shipping | نقض صریح بند ۸ بریف («هیچ API ای نباید حدس زده شود») -- کارفرما هم صریحاً «فقط داخلی» را انتخاب کرد |
| اتصال Returns به یک Wallet که هنوز وجود ندارد | جلو انداختن بخشی از ماژول Wallet خارج از ترتیب فازها؛ کارفرما هم صریحاً گردش‌کار-محور را انتخاب کرد |

## Consequences

**مثبت:** ماژول `payments` هیچ تغییری نیاز نداشت (فقط یک Migration برای گشاد کردن CHECK Constraint) -- دقیقاً همان ادعای ADR-0011 که در عمل هم درست از آب درآمد.

**ریسک/نیازمند توجه:**
- تا وقتی یک Provider واقعی باربری/پستی متصل نشود، مرحله‌ی «ارسال واقعی» کاملاً دستی (ثبت شماره پیگیری توسط ادمین، خارج از این سیستم) باقی می‌ماند.
- `requires_manual_review` روی سفارش‌ها باید در Admin Panel (Phase 14) به‌صورت یک فیلتر/هشدار قابل‌مشاهده باشد -- در این فاز فقط ستون دیتابیسی و منطق ست‌شدنش پیاده‌سازی شده، نه UI مدیریت آن.
- بازگشت وجه مرجوعی‌ها کاملاً دستی است -- اگر تعداد مرجوعی‌ها زیاد شود، این یک محدودیت عملیاتی واقعی برای تیم پشتیبانی خواهد بود، نه فقط یک نکته‌ی فنی.
