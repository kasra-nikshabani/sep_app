# ADR-0015: Notifications و Partners (اسکلت ساختاری)

- **وضعیت:** پذیرفته‌شده (Phase 13)
- **تصمیم‌گیرندگان:** Architect + کارفرما (دو فرک واقعی از طریق AskUserQuestion قبل از شروع پیاده‌سازی تأیید شدند)

## Context

طبق بند ۱ بریف (فهرست فازها)، Phase 13 با عنوان «External Integrations» برنامه‌ریزی شده بود. طبق بند ۷/۸ بریف، حوزه‌های واقعی این فاز `Banking`, `Vehicle`, `Insurance`, `Travel`, `Entertainment` هستند، با فهرست Providerهای «مورد بررسی» (نه تأییدشده): آیتول، سابیم، CityNet، iHotelHub، CinemaTicket، IranTicket، Banking/Open Banking. بند ۸ بریف صریح می‌گوید: **«هرگز API را حدس نزن»**.

بررسی واقعی (نه فرض) نشان داد هیچ‌کدام از این‌ها در سیستم Django موجود یا جای دیگری این پروژه استفاده نشده‌اند -- برخلاف SMS.ir و SMTP (Gmail) که هر دو واقعاً در تنظیمات فعلی Django پیکربندی شده‌اند. از طرفی، خودِ بریف «Notifications» را یک فاز کاملاً جدا (Phase 16) تعریف کرده است.

با AskUserQuestion این وضعیت به‌صراحت با کارفرما مطرح شد و دو تصمیم گرفته شد:
1. چهار حوزه‌ی `Banking/Vehicle/Insurance/Travel/Entertainment` **کاملاً کنار گذاشته شوند** -- حتی ساختن یک Interface خالی برای آن‌ها بدون هیچ API واقعی برای شکل‌دادن به آن، خودش نوعی حدس‌زدن است.
2. به‌جای آن، محتوای واقعی Phase 16 (Notifications) به همین فاز منتقل شود (چون Providerهای واقعی و آماده دارد)، به‌علاوه‌ی اسکلت ساختاری Partners (که rbac-matrix.md صریحاً Phase 13 را برایش نشانه گرفته بود).

## Decision

### 1) SMS: SMS.ir، تحقیق‌شده در همین فاز (نه حدس)

مستندات رسمی `sms.ir/rest-api/` بررسی شد (Endpoint `POST https://api.sms.ir/v1/send/bulk`، Header `X-API-KEY`، بدنه‌ی `{lineNumber, messageText, mobiles}`، پاسخ `{status, message, data}`؛ `status=1` یعنی موفق). همان Provider ای که سیستم فوتبال Django از قبل واقعاً استفاده می‌کند (`SMS_IR_API_KEY` در تنظیمات آن) -- یکسان‌سازی Provider بین دو سیستم، هم‌روح تصمیم Zibal در ADR-0011.

**تفاوت مهم با Zibal در تست:** SMS.ir هیچ Sandbox عمومی رایگان مثل `merchant: zibal` ندارد -- هر پیامک واقعی هزینه‌ی واقعی دارد. به همین دلیل، برخلاف `ZibalPaymentProviderTest` (که مستقیم Sandbox واقعی را می‌زند)، `SmsIrProvider` تست خودکار زنده ندارد؛ تست فقط از طریق `FakeSmsProvider` (پیش‌فرض) پوشش داده شده. قبل از فعال‌کردن `sms_ir` در Production، یک تست دستی با یک شماره‌ی واقعی توسط کارفرما/تیم پیشنهاد می‌شود.

### 2) Email: SMTP استاندارد -- یک Dependency جدید، با تأیید صریح

پیاده‌سازی واقعی نیازمند `spring-boot-starter-mail` بود (طبق بند ۲۶ بریف، قبل از افزودن هر Dependency جدید تأیید کارفرما لازم است) -- **تأیید گرفته شد**. هیچ Credential واقعی SMTP برای این سیستم جدید هنوز وجود ندارد؛ پیاده‌سازی آماده است اما پیکربندی واقعی (Host/Username/Password) قبل از Production باید جایگزین شود -- دقیقاً هم‌الگوی محدودیت Merchant ID موقت Zibal در ADR-0011.

### 3) Push: فقط Fake -- اتصال واقعی حدس‌زدن API بود

بدون اپ موبایل واقعی (Phase 15 هنوز ساخته نشده) و بدون هیچ تصمیم روی FCM در برابر APNs یا هر Provider دیگر، پیاده‌سازی یک Provider واقعی Push دقیقاً همان «حدس‌زدن API» ای بود که بند ۸ بریف منع کرده. `FakePushProvider` (فقط Log) تنها پیاده‌سازی این فاز است. ثبت/لغو Device Token اما واقعی و کامل است -- زیرساخت لازم صرف‌نظر از این‌که کدام Provider بعداً انتخاب شود.

### 4) ارسال Notification همیشه Best-effort است

`NotificationService` هرگز Exception یک Provider را به فراخوانی‌کننده پرتاب نمی‌کند -- شکست در `NotificationLog` با `status=failed` ثبت می‌شود. دلیل: یک پیامک/ایمیل ناموفق نباید یک عملیات کسب‌وکاری (مثلاً ثبت سفارش) را Rollback کند. این فاز هیچ ماژول قبلی (Shop/Ticketing/Loyalty/News) را برای فراخوانی خودکار Notification تغییر نداده -- زیرساخت آماده و مستقل تست شده است؛ اتصال خودکار (مثلاً «پیامک تأیید سفارش») موضوع فازی است که آن رویداد مشخص را نیاز داشته باشد، نه این فاز.

### 5) Partners: فقط اسکلت ساختاری، طبق rbac-matrix.md

`Partner` یک رکورد ادمین-مدیریت‌شده با یک کلید API تولیدشده است. کلید خام فقط یک‌بار، در پاسخ ساخت، نمایش داده می‌شود؛ در دیتابیس فقط SHA-256 آن ذخیره می‌شود (نه bcrypt -- دلیل در کامنت Migration V10: کلید یک راز پرآنتروپی تولیدشده است، نه رمز عبور کاربر؛ هش قطعی برای جست‌وجوی مستقیم لازم است). `PartnerSelfController.GET /api/v1/partners/me` تنها مسیری است که خودِ Partner می‌بیند -- با کلید خودش احراز هویت می‌شود (نه Keycloak، نه Admin Panel)، هم‌الگوی استثنای Callback پرداخت در SecurityConfig (ADR-0011). طراحی دقیق داده/API واقعی هر Partner، وقتی یک Partner واقعی امضا شود، موضوع فاز خودش خواهد بود -- این‌جا حدس زده نشده.

## Alternatives Considered

| گزینه | چرا رد شد |
|---|---|
| ساختن Interface عمومی برای Insurance/Vehicle/Travel/Entertainment با یک Fake Provider | حتی شکل یک Interface بدون هیچ API واقعی برای مرجع‌قراردادن، نوعی حدس‌زدن است -- طبق تصمیم صریح کارفرما رد شد |
| صبر کامل تا Phase 16 برای هر نوع Notification | Partners تنها می‌ماند و این فاز عملاً خالی می‌شد؛ SMS.ir/SMTP هر دو همین الان قابل تحقیق و پیاده‌سازی واقعی بودند |
| هش bcrypt برای کلید API Partner | Overhead بی‌دلیل -- bcrypt برای رمزهای کم‌آنتروپی کاربر طراحی شده؛ کلید API یک راز ۲۵۶ بیتی تصادفی است که نیاز به جست‌وجوی مستقیم (نه تطبیق تدریجی) دارد |

## Consequences

**مثبت:** ماژول‌های Shop/Ticketing/Loyalty/News هیچ تغییری نیاز نداشتند. بدون Dependency جدید غیرضروری (فقط یک مورد، تأییدشده).

**ریسک/نیازمند توجه:**
- Push کاملاً غیرفعال است تا Phase 15 (اپ موبایل) و یک تصمیم واقعی روی Provider.
- SMS.ir فقط با تست دستی (نه خودکار) قبل از Production قابل تأیید نهایی است -- هزینه‌ی واقعی هر پیامک.
- هیچ ماژول دیگری هنوز به این سرویس متصل نیست -- ارزش واقعی آن با اولین اتصال (مثلاً تأییدیه‌ی سفارش) محقق می‌شود.
- چهار حوزه‌ی کنارگذاشته‌شده (Banking/Vehicle/Insurance/Travel/Entertainment) هنوز در برنامه‌ی محصول باقی می‌مانند -- نیازمند یک فاز/تصمیم آینده وقتی یک Provider واقعی انتخاب شود.
