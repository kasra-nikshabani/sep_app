# ADR-0014: ماژول Loyalty

- **وضعیت:** پذیرفته‌شده (Phase 12)
- **تصمیم‌گیرندگان:** Architect + کارفرما (یک فرک واقعی از طریق AskUserQuestion قبل از شروع پیاده‌سازی تأیید شد)

## Context

طبق بند ۱۶ بریف: `Fan -> Loyalty Account -> Points/Level/Rewards/Transactions`، و «سطوح عضویت و منطق امتیازدهی باید Configurable باشند، Hard-code نکن». طبق [ADR-0002](0002-modular-monolith-and-module-boundaries.md) (فاز طراحی اولیه)، منبع رویداد امتیاز شامل خرید Shop و بلیط تئاتر است، **و اتصال به رویداد خرید بلیط فوتبال از Django موضوع همین فاز است**.

اتصال به Django یعنی دوباره باید کد سیستم زنده‌ی فوتبال را تغییر داد (مثل Phase 7) -- یک فرک معماری واقعی که از طریق AskUserQuestion مطرح شد: کارفرما **«Polling از یک API جدید Django»** را انتخاب کرد (نه Webhook، نه کنار گذاشتن این اتصال).

## Decision

### 1) سطح/امتیاز/جایزه همه Configurable هستند (طبق بند ۱۶ بریف)

`LoyaltyLevel` و `PointsEarningRule` جدول‌های عادی‌اند که ادمین مدیریت می‌کند -- نه Enum ثابت در کد. نرخ امتیازدهی هر منبع رویداد (`shop_order`, `ticket_purchase`, `football_ticket_purchase`) جدا تعریف می‌شود؛ حداکثر یک قانون فعال به‌ازای هر منبع (Partial Unique Index دیتابیسی).

### 2) سطح بر اساس `lifetimePoints` است، نه `pointsBalance`

`lifetimePoints` هرگز با خرج‌کردن امتیاز کم نمی‌شود؛ سطح عضویت روی همین مبنا محاسبه می‌شود. این یعنی خرج‌کردن امتیاز برای یک جایزه هرگز باعث افت سطح عضویت نمی‌شود -- یک تصمیم محصولی معقول که مستقیماً از دو ستون جدا (نه یک ستون با منطق پیچیده‌ی بازسازی از دفترکل) پشتیبانی می‌شود.

### 3) کاهش اتمی موجودی امتیاز/جایزه در دیتابیس -- هم‌الگوی Shop (ADR-0012)

`decrementSpentPoints`/`decrementStock` با شرط محافظتی در همان `UPDATE` (نه قفل Redis، نه بررسی-سپس-نوشتن در کد جاوا). تست شده با ۲۰ تلاش واقعاً هم‌زمان روی آخرین واحد موجودی یک جایزه.

**باگ واقعی کشف‌شده و رفع‌شده (دو مرحله‌ای):**
1. بدون `clearAutomatically`، وقتی همان Entity قبلاً در همین Transaction بارگذاری شده بود (مثلاً توسط `getOrCreateAccount`)، یک `save()` بعدی (برای تغییر سطح) مقدار صحیحِ همین `UPDATE` اتمی را با مقدار قدیمیِ در Persistence Context بازنویسی می‌کرد -- امتیاز واقعاً اضافه می‌شد ولی بلافاصله توسط `recomputeLevel` صفر می‌شد.
2. رفع اول (`clearAutomatically = true` به‌تنهایی) یک باگ **بدتر** ایجاد کرد: بدون `flushAutomatically = true` همراهش، `clearAutomatically` حافظه‌ی Entityهای هنوز Flush-نشده‌ی همان Transaction (مثلاً یک `Order` تازه‌ساخته‌شده در Shop) را بدون نوشتن روی دیتابیس دور می‌ریزد -- با اجرای مجدد کل مجموعه‌ی تست‌ها (نه فقط تست‌های همین فاز) بلافاصله به شکل خطای FK Constraint واقعی در ماژول Shop ظاهر شد. رفع نهایی: `@Modifying(flushAutomatically = true, clearAutomatically = true)` روی هر سه Repository ای که این الگو را دارند (`LoyaltyAccountRepository`, `LoyaltyRewardRepository`, و پیشگیرانه `shop.ProductVariantRepository`).

این یک یادآوری واقعی است که چرا این پروژه بعد از هر تغییر، کل مجموعه‌ی تست‌ها را دوباره اجرا می‌کند، نه فقط تست‌های ماژول تغییریافته.

### 4) اتصال بلیط فوتبال: Polling، نه Webhook

Django یک Endpoint **فقط-خواندنی** جدید می‌گیرد (`tickets/api_loyalty.py`، `GET /tickets/api/loyalty/completed-orders/?since=...`) که سفارش‌های `payment_status='paid'` را برمی‌گرداند. Backend (Spring Boot) هر ۵ دقیقه آن را Poll می‌کند.

**چرا Polling، نه Webhook (تصمیم صریح کارفرما):** Webhook یعنی Django باید در همان مسیر همزمان تکمیل خرید یک وابستگی جدید به یک سیستم خارجی (این Backend) اضافه کند -- دقیقاً همان نوع تغییر ساختاری که بریف می‌خواهد از آن پرهیز شود («سیستم Django فعلی دست‌نخورده می‌ماند»). Polling یعنی منطق خرید/پرداخت Django کاملاً دست‌نخورده می‌ماند؛ فقط یک مسیر گزارش‌گیری اضافه شده. Polling همچنین ذاتاً خودترمیم است: اگر این Backend یا شبکه موقتاً از دسترس خارج شود، Poll بعدی همان بازه را دوباره می‌خواند -- بدون نیاز به مکانیزم Retry/Queue جدا در سمت Django.

**احراز هویت Endpoint جدید Django:** نه Keycloak (Middleware فعلی Keycloak کاربر Fan را احراز هویت می‌کند، نه یک سرویس -- توکنی که ادعا/Claim کاربر واقعی نداشته باشد را اصلاً قبول نمی‌کند)؛ یک راز مشترک ساده (`LOYALTY_POLL_SERVICE_TOKEN`)، هم‌الگوی مکانیزم موجود `GATE_USERS` در همان پروژه برای ورود گیت.

**کشف واقعی حین تست زنده (نه در طراحی):** `GeoAccessMiddleware` موجود در Django (که بازدید از IP خارج از ایران را با ۴۰۳ رد می‌کند) این Endpoint را هم می‌گرفت -- چون هدر `X-Iran-IP` فقط توسط nginx برای بازدید واقعی تنظیم می‌شود، نه برای تماس مستقیم Backend به Backend. رفع شد با افزودن این مسیر به `GEO_EXEMPT_PREFIXES` (هم‌الگوی استثنای موجود `/admin/`).

### 5) الگوی Cursor: بر اساس زمان خود Django، نه ساعت این Backend

Cursor (`loyalty.external_poll_cursor`) فقط بر اساس بیشینه‌ی `paid_at` واقعی دیده‌شده در پاسخ Django جلو می‌رود، به‌علاوه‌ی یک بازه‌ی همپوشانی ثابت (۵ دقیقه) در هر Query. این یعنی حتی اگر یک سفارش کمی دیرتر از حد انتظار در Django Commit شود، Poll بعدی دوباره آن را می‌بیند -- بدون خطر امتیاز تکراری، چون هر رویداد با `(football_ticket_purchase, ارجاع سفارش)` در سطح دیتابیس Idempotent است (Partial Unique Index، هم‌الگوی Payment در ADR-0011).

`sourceReferenceId` یک UUID قطعی و پایدار از روی `order_number` سفارش Django است (`UUID.nameUUIDFromBytes`) -- چون شناسه‌ی طبیعی Django عدد صحیح است، نه UUID، ولی ستون `source_reference_id` در همه‌ی ماژول‌ها (طبق قرارداد یکسان) از نوع UUID است.

**محدودیت مستند، نه حدس:** کاربرانی که هرگز با Fan ID (Keycloak) وارد نشده‌اند `fan_id_subject` ندارند (Nullable در Django، طبق Phase 7) و فعلاً امتیازی نمی‌گیرند -- تنها راه واقعی تطبیق این‌جا `fan_id_subject` است، نه حدس زدن بر اساس کد ملی/شماره تلفن (که فرمت متفاوت بین دو سیستم می‌تواند اشتباه Match کند).

### 6) Rewards: بدون تحویل خودکار واقعی

مبادله (`RewardRedemption`) فقط یک کد یکتا صادر می‌کند؛ تحویل فیزیکی/دیجیتال کاملاً دستی توسط ادمین است (هم‌الگوی `shop.ReturnService`، ADR-0012) -- هیچ سیستم ارسال/تحویل واقعی در این فاز بریف ذکر نشده.

## Alternatives Considered

| گزینه | چرا رد شد |
|---|---|
| Webhook از Django به‌محض تکمیل خرید | نیازمند وابستگی همزمان جدید در مسیر خرید Django به یک سیستم خارجی؛ اگر آن درخواست شکست بخورد، بدون یک Retry Queue جدا (سربار بیشتر روی سیستمی که باید دست‌نخورده بماند)، امتیاز برای همیشه گم می‌شود |
| سطح عضویت بر اساس `pointsBalance` | خرج‌کردن امتیاز باعث افت غیرمنصفانه‌ی سطح می‌شد -- تجربه‌ی کاربری بد برای یک برنامه‌ی وفاداری |
| قفل Redis برای موجودی جایزه/امتیاز (هم‌الگوی صندلی تئاتر) | هر دو یک Pool تعداد هستند، نه یک منبع منحصربه‌فرد -- یک UPDATE اتمی دیتابیسی همان تضمین را می‌دهد (طبق همان استدلال ADR-0012) |

## Consequences

**مثبت:** ماژول‌های `shop`/`ticketing`/`payments` هیچ تغییری نیاز نداشتند -- فقط یک Listener جدید روی همان `PaymentSucceededEvent` موجود، دقیقاً همان ادعای ADR-0011 که در عمل دوباره درست از آب درآمد.

**ریسک/نیازمند توجه:**
- ذخیره‌سازی/تحویل جایزه کاملاً دستی است -- اگر تعداد مبادله‌ها زیاد شود، محدودیت عملیاتی واقعی برای تیم پشتیبانی خواهد بود.
- اتصال Django فعلاً روی یک راز مشترک ساده است، نه Keycloak Client Credentials -- اگر در آینده تصمیم به یکسان‌سازی مکانیزم احراز هویت سرویس‌به‌سرویس گرفته شد، این بخش باید بازبینی شود.
- کاربران بدون ورود از طریق Fan ID فعلاً امتیاز بلیط فوتبال نمی‌گیرند -- این محدودیت با گذر زمان (با ورود بیشتر کاربران از طریق SSO) خودبه‌خود کمتر می‌شود، نیازی به اقدام فوری ندارد.
- تست زنده‌به‌زنده‌ی کامل Polling با دیتابیس واقعی Django ممکن نشد چون دیتابیس محلی `sepahan_ticket` با Modelهای فعلی هم‌خوان نبود (یک Migration از قبل روی آن اجرا نشده بود -- کاملاً بی‌ربط به این فاز). تست‌های واحد Django (SQLite) + تست‌های JUnit این پروژه + تأیید زنده‌ی لایه‌ی Auth/Routing (۴۰۱/۴۰۰ واقعی از Django) جایگزین آن شدند.
