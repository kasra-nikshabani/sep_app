# ADR-0023: اتصال حساب Fan ID به سایت بلیط -- فقط بعد از یک OTP، و دکمه‌ی «ورود با Fan ID»

- **وضعیت:** Merge شده در `main` ریپوی سایت بلیط (پیش‌فرض خاموش)؛ روشن شدن روی سایت زنده منتظر Keycloak عمومی است
- **تصمیم‌گیرندگان:** کارفرما + Architect
- **جایگزین بخشی از:** [ADR-0004](0004-django-ticketing-sso-integration.md) (نگاشت بر اساس کد ملی) و [ADR-0008](0008-new-user-jit-provisioning.md) (JIT از روی توکن)

## Context

هدف کارفرما: کاربری که در اپ ثبت‌نام کرده، در سایت بلیط دوباره ثبت‌نام نکند و هر بار کد
ورود نگیرد؛ و خرید بلیطش به باشگاه امتیاز برسد.

پیاده‌سازی Phase 7 (ADR-0004/0008) حساب موجود سایت را با `national_code` داخل توکن پیدا
می‌کرد و بی‌صدا به همان Fan ID وصل می‌کرد، و کاربر تازه را با `is_phone_verified=True`
می‌ساخت -- با این فرض که ثبت‌نام Fan ID شماره را با OTP تأیید کرده است. **این فرض درست
نیست:** ثبت‌نام Keycloak فقط فرمت کد ملی و شماره را بررسی می‌کند، نه مالکیت و نه یکتا
بودن کد ملی. نتیجه: هر کس با کد ملی شخص دیگری در اپ ثبت‌نام می‌کرد، حساب او در سایت بلیط
(بلیط‌ها، کیف پول) و امتیازهایش را تصاحب می‌کرد. این کد هرگز Deploy نشده بود.

## Decision

1. **مسیر Bearer (اپ → سایت)** دیگر هیچ حسابی نمی‌سازد و متصل نمی‌کند؛ فقط کاربری را
   می‌شناسد که `fan_id_subject` آن از قبل برابر `sub` توکن است (و فقط کاربر عادی).
2. **اتصال فقط یک‌بار و فقط در مسیر مرورگر** (دکمه‌ی «ورود با Fan ID» در صفحه‌ی ورود و
   ثبت‌نام سایت): OIDC Authorization Code + PKCE (S256) با state و nonce، سپس یک OTP با همان
   `create_otp`/`get_valid_otp` خود سایت:
   - حساب موجود با همان کد ملی → کد به **شماره‌ای که خود سایت از قبل دارد**، نه شماره‌ی توکن.
   - حسابی نیست → کد به شماره‌ی Fan ID و حساب بعد از تأیید ساخته می‌شود.
   - حساب متصل به Fan ID دیگر، حساب ادمین/VIP، و تداخل شماره با کد ملی دیگر → رد، ارجاع به پشتیبانی.
3. بعد از اتصال، ورودهای بعدی بدون هیچ کدی انجام می‌شود (اگر نشست Keycloak باز باشد، فقط یک کلیک).
4. Client همان `django-ticketing` است (ADR-0003) که از bearer-only به Confidential با
   Standard Flow + PKCE تبدیل شد؛ Secret فقط در `.env` سرور سایت (`FANID_CLIENT_SECRET`).
5. همه‌چیز پیش‌فرض خاموش است (`FANID_LOGIN_ENABLED` + Secret + آدرس بازگشت)؛ تا روشن
   نشود مسیرها ۴۰۴ می‌دهند و دکمه‌ای نمایش داده نمی‌شود.

## Alternatives Considered

| گزینه | چرا انتخاب نشد |
|---|---|
| تأیید شماره با پیامک در خود ثبت‌نام Keycloak (بدون هیچ OTP در سایت) | نیازمند Extension/SPI سفارشی Keycloak (Keycloak پیامک ندارد) -- بزرگ‌تر و حساس‌تر؛ و برای حساب‌های موجود سایت که شماره‌شان با Fan ID فرق دارد باز هم اثبات مالکیت لازم است. می‌تواند بعداً اضافه شود. |
| نگه داشتن اتصال بر اساس کد ملی | همان آسیب‌پذیری تصاحب حساب. |
| یک Client جدید برای ورود مرورگری | `django-ticketing` از قبل Client ثبت‌شده‌ی همین سیستم بود و استفاده نمی‌شد؛ دو Client برای یک سیستم بی‌دلیل. |

## Consequences

- هر کاربر فقط **یک بار** در عمر حسابش یک کد می‌گیرد؛ این همان سطح اعتماد ثبت‌نام فعلی سایت است، نه ضعیف‌تر.
- امتیاز خرید بلیط (ADR-0014) از همان `fan_id_subject` است، پس فقط بعد از اتصال به حساب درست می‌رسد.
- تست‌ها: ۱۸۷ تست کل سایت سبز (۱۵۰ تست قبلی + ۳۷ تست Fan ID/Loyalty، شامل تست تصاحب حساب)، با
  Postgres یک‌بارمصرف؛ و یک تست end-to-end محلی با Keycloak واقعی (ورود اول با OTP، ورود دوم بدون کد،
  و ارسال کد به شماره‌ی ثبت‌شده‌ی سایت برای حساب موجود).
- اپ: کاشی «بلیط مسابقات» سایت بلیط را در مرورگر داخل اپ باز می‌کند (روی وب: تب تازه). آدرس از
  `EXPO_PUBLIC_TICKET_SITE_URL` می‌آید: تا «ورود با Fan ID» روی سایت روشن نشده `…/matches/`، بعد از آن
  `…/accounts/fanid/login/?next=/matches/` -- همان لحظه وارد می‌شود، بدون تغییر کد. روی آیفون مرورگر داخل
  اپ کوکی‌های ورود اپ را نمی‌بیند، پس ممکن است یک بار فرم ورود Fan ID نشان داده شود.
- یکتا بودن کد ملی در Keycloak: حل شد -- کد ملی همان نام کاربری Fan ID است ([ADR-0024](0024-national-code-as-fan-id-username.md)).
- هنوز باز: امتیاز خریدهای قبل از اتصال (تصمیم باشگاه)؛ روشن کردن روی سایت زنده بعد از Deploy عمومی
  Keycloak (توسط تیم سایت بلیط).
