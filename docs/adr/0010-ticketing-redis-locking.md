# ADR-0010: قفل هم‌زمانی رزرو صندلی با Redis

- **وضعیت:** پذیرفته‌شده (Phase 8)
- **تصمیم‌گیرندگان:** Architect (تصمیم پیاده‌سازی درون‌فازی، در چهارچوب ADR-0006 از قبل تأییدشده)

## Context

طبق [ADR-0006](0006-inhouse-theater-ticketing.md)، موتور بلیط تئاتر باید هم‌زمانی رزرو صندلی را ایمن مدیریت کند. سیستم فوتبال Django موجود دقیقاً همین مسئله را قبلاً داشته: بدون قفل درست، دو کاربر می‌توانستند هم‌زمان یک صندلی را رزرو کنند، یا (نمونه‌ی مشابه‌تر) دو درخواست هم‌زمان بیش از موجودی واقعی کیف‌پول/سهمیه‌ی VIP/کد تخفیف را مصرف کنند — طبق گزارش موجود آن سیستم، این مشکل با UPDATE اتمیک سطح دیتابیس رفع شد.

برای رزرو صندلی، تنها Constraint دیتابیس (مثلاً Unique روی `event_seat_id` در جدول `reservation`) کافی نیست، چون هدف «رد سریع و قبل از هرگونه نوشتن دیتابیس» است، نه فقط جلوگیری از نوشتن دوتایی.

## Decision

قفل اتمیک در **Redis** با دستور `SET key value NX EX <ttl>` روی کلید `seat-lock:<event_seat_id>`:

1. کاربر تلاش می‌کند صندلی را رزرو کند → ابتدا `SET NX` روی Redis؛ اگر کلید از قبل وجود داشت (یعنی صندلی همین الان توسط کس دیگری در حال رزرو یا رزروشده است) → رد فوری، بدون هیچ تماس با دیتابیس.
2. اگر قفل گرفته شد → ردیف `RESERVATION` در Postgres ساخته می‌شود (Source of Truth برای گزارش‌گیری/Audit) با `expires_at` برابر با TTL همان قفل Redis.
3. با انقضای TTL در Redis، قفل خودکار آزاد می‌شود؛ یک Job پاک‌سازی دوره‌ای (Scheduled)، ردیف‌های `RESERVATION` منقضی‌شده در Postgres را هم پاک می‌کند (چون Redis به‌تنهایی دیتابیس را تمیز نمی‌کند).
4. بعد از تکمیل (فعلاً ساده‌شده، بدون پرداخت واقعی — Phase 9)، `TICKET` ساخته و قفل Redis + ردیف `RESERVATION` صریحاً آزاد می‌شوند.

## Alternatives Considered

| گزینه | چرا رد شد |
|---|---|
| فقط `SELECT ... FOR UPDATE` سطح دیتابیس | همان مشکلی که باعث افزودن صف پس‌زمینه‌ی PDF در Django شد را تکرار می‌کند: تحت بار بالا (خرید هم‌زمان بلیط یک اجرای پرطرفدار)، قفل‌های سطح ردیف روی خود جدول اصلی می‌توانند صف طولانی درست کنند؛ Redis این فشار را از دیتابیس دور نگه می‌دارد |
| Optimistic Locking (نسخه‌ی ردیف + Retry) | برای تعداد صندلی محدود و رقابت بالا (لحظه‌ی شروع فروش)، تعداد Retry ناموفق می‌تواند تجربه‌ی کاربری بدی بسازد؛ قفل بدبینانه‌ی سریع (Redis) برای این سناریوی خاص مناسب‌تر است |

## Consequences

**مثبت:** رد سریع بدون فشار به دیتابیس؛ الگوی ثابت با تجربه‌ی اثبات‌شده‌ی سیستم فوتبال (هرچند کاملاً کد/زیرساخت مستقل).

**ریسک/نیازمند توجه:** اگر Redis از دسترس خارج شود، رزرو صندلی هم متوقف می‌شود (Redis این‌جا یک وابستگی سخت است، نه صرفاً Cache). این Tradeoff آگاهانه پذیرفته شد چون Redis از قبل یک وابستگی سخت زیرساخت پروژه است (Session/Cache در چند جای دیگر هم همین الان به آن متکی است).
