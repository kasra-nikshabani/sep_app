# ADR-0006: موتور داخلی فروش بلیط تئاتر

- **وضعیت:** پذیرفته‌شده (تصمیم صریح کارفرما، 2026-08-15)
- **تصمیم‌گیرندگان:** کارفرما + Architect

## Context

بریف اولیه (بخش ۳) «فروش بلیط تئاتر» را در کنار سینما و کنسرت به‌عنوان یکی از سرویس‌های سرگرمی فهرست کرده بود که به‌طور ضمنی می‌توانست از طریق Providerهای بیرونی (مثل CinemaTicket/IranTicket که در بند ۸ بریف آمده‌اند) پوشش داده شود. کارفرما صراحتاً اعلام کرد:

> «بخش خرید بلیط تئاتر، از سمت provider نباید بیاد، خودمون باید هندل کنیم.»

## Decision

فروش بلیط تئاتر **کاملاً داخلی و اول‌شخص** (In-house) پیاده‌سازی می‌شود — **بدون هیچ Adapter Provider خارجی**. این قابلیت از ماژول جدید `ticketing` (معرفی‌شده در [ADR-0002](0002-modular-monolith-and-module-boundaries.md)) استفاده می‌کند که از ابتدا با یک مدل دامنه‌ی **عمومی** طراحی می‌شود:

```
Venue (سالن) → Section/Block → Row → Seat
Event (اجرای نمایش، در تاریخ/ساعت مشخص) → EventSeat (وضعیت هر صندلی برای آن اجرا)
Reservation (رزرو موقت، مشابه الگوی Redis-lock موجود در Django برای هم‌زمانی)
Ticket (QR، PDF، اعتبارسنجی در محل)
```

این مدل عمداً با نام‌های عمومی (`Venue`/`Event` به‌جای `Stadium`/`Match`) طراحی می‌شود تا:

1. برای تئاتر همین حالا قابل استفاده باشد.
2. در آینده، اگر تصمیم به پوشش سینما/کنسرت به‌صورت داخلی هم گرفته شد (فعلاً **خیر** — طبق تصمیم امروز کارفرما، سینما/کنسرت همچنان Provider-based می‌مانند)، بدون بازنویسی ساختار دیتابیس قابل توسعه باشد.
3. **هیچ ارتباطی با مدل داده‌ی Django فوتبال ندارد** و کد آن را import/reuse نمی‌کند — سیستم کاملاً مستقل و جدید است، صرفاً از نظر مفهومی (نه کد) از الگوی اثبات‌شده‌ی Django (Redis Lock برای هم‌زمانی رزرو صندلی، QR+اعتبارسنجی در محل) الهام می‌گیرد.

### پوشش عملیاتی مشابه بند ۱۴ بریف

Venue، Section، Row، Seat، Reservation، Payment (از طریق ماژول مرکزی `payments`، طبق [ADR-0005](0005-integration-provider-pattern.md))، Ticket، QR Code، Validation — همه‌ی این‌ها برای تئاتر پیاده‌سازی می‌شوند.

## Alternatives Considered

| گزینه | چرا رد شد |
|---|---|
| استفاده از Provider بیرونی مثل IranTicket/CinemaTicket برای تئاتر | **رد شریح توسط کارفرما** — دلیل کسب‌وکاری (کنترل کامل روی قیمت‌گذاری/موجودی/تجربه‌ی کاربری بلیط تئاتر، بدون وابستگی/کارمزد Provider ثالث) |
| توسعه‌ی مستقیم مدل Django فوتبال (Stadium/Block/Row/Seat) برای تئاتر هم | رد شد — نقض بند ۶ بریف (Django نباید توسعه/بازنویسی ساختاری شود) و ایجاد وابستگی نامناسب بین یک سیستم Legacy مجزا و یک قابلیت کاملاً جدید |
| یک ماژول کاملاً جدا به‌نام `theater` به‌جای `ticketing` عمومی | رد شد — اگر بعداً کنسرت/سینمای داخلی هم لازم شد (تصمیم آینده)، بازنویسی کامل لازم می‌شد؛ نام‌گذاری عمومی از ابتدا هزینه‌ی تقریباً صفر دارد ولی گزینه‌ی توسعه را باز نگه می‌دارد |

## Consequences

**مثبت:** کنترل کامل روی تجربه‌ی خرید بلیط تئاتر (قیمت، ظرفیت، Cancellation Policy) بدون وابستگی به SLA/Downtime یک Provider ثالث؛ معماری داده آماده‌ی توسعه‌ی آینده بدون بدهی فنی.

**نیازمند توجه:**
- این یعنی تیم توسعه باید تمام پیچیدگی‌هایی که Django برای فوتبال قبلاً حل کرده (Race Condition رزرو هم‌زمان، تولید PDF/QR با کارایی مناسب، امنیت مسیر دانلود بلیط) را از نو برای تئاتر حل کند — نه یک بار Copy-paste ساده. این باید در برآورد زمانی Phase 8/9 لحاظ شود.
- محتوای واقعی تئاترها (کدام سالن‌ها، ظرفیت واقعی، قرارداد با سالن‌های تئاتر) داده‌ی کسب‌وکاری است که باید از کارفرما دریافت شود — خارج از محدوده‌ی فنی این ADR.

## Open Questions

- آیا مدیریت محتوای Event تئاتر (افزودن اجرای جدید، تعیین قیمت) از همان Admin Panel جدید انجام می‌شود؟ (فرض پیش‌فرض: بله، مشابه بند ۱۸ بریف) — تأیید در Phase 14.
