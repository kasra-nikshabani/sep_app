# ADR-0024: کد ملی = نام کاربری Fan ID (یک کد ملی، فقط یک حساب)

- **وضعیت:** پذیرفته شده (انتخاب کارفرما)؛ پیاده‌سازی و تأیید شده روی Keycloak محلی و یک Import تازه
- **تصمیم‌گیرندگان:** کارفرما + Architect
- **اصلاح بخشی از:** [ADR-0003](0003-keycloak-central-sso-fan-id.md) (کد ملی به‌عنوان User Attribute جدا)

## Context

ثبت‌نام Fan ID فقط **فرمت** کد ملی را بررسی می‌کرد، نه **یکتا بودن** آن را. Keycloak برای Attributeهای
دلخواه هیچ Validator یکتایی داخلی ندارد (فقط برای نام کاربری و ایمیل). پس یک نفر می‌توانست چند حساب
Fan ID با یک کد ملی بسازد -- و همین اتفاق واقعاً افتاد: یک کاربر دو حساب با یک کد ملی داشت. سایت بلیط
حسابش را به یکی متصل کرده بود و با ورود از دیگری، طبق [ADR-0023](0023-fanid-account-linking-ticket-site.md)
درست رد شد («حساب سایت بلیط با این کد ملی قبلاً به حساب Fan ID دیگری متصل شده است»). Backend اپ هم همین
مشکل را دارد: `users.app_user.national_code` یکتاست، پس اولین ورود حساب دوم (JIT) با خطای ۵۰۰ شکست می‌خورد.

رد کردن در سایت بلیط درست است؛ ریشه باید در خود Fan ID بسته شود: هر کد ملی فقط یک حساب.

## Decision

1. **نام کاربری Fan ID همان کد ملی است.** در پروفایل کاربر (Declarative User Profile)، `username`
   اعتبارسنجی `^[0-9]{10}$` دارد («کد ملی باید دقیقاً ۱۰ رقم باشد»). یکتا بودن نام کاربری را خود Keycloak
   تضمین می‌کند؛ ثبت‌نام دوم با همان کد ملی رد می‌شود («با این کد ملی قبلاً حساب ساخته شده است…»).
2. Attribute جدای `national_code` از پروفایل حذف شد. Mapper `national-code` در Scope `fan-identity`
   حالا از `username` می‌خواند، پس Claim `national_code` برای Backend و سایت بلیط **همان است** -- بدون
   هیچ تغییر کد در مصرف‌کننده‌ها.
3. `editUsernameAllowed: false` (از قبل): کاربر بعد از ثبت‌نام نمی‌تواند کد ملی را عوض کند.
4. متن صفحه‌ی ورود/ثبت‌نام: «نام کاربری» ← «کد ملی» (`infra/keycloak/themes/sepahan/login/messages/messages_fa.properties`).
5. پروفایل فقط یک منبع دارد: `sepahan-realm.json`. `infra/keycloak/fix-user-profile.sh` که قبلاً کپی
   قدیمی خودش را داشت (و اجرایش این تصمیم و اعتبارسنجی‌های ثبت‌نام را بی‌صدا برمی‌گرداند) حالا
   همان پروفایل فایل را اعمال می‌کند.

## Alternatives Considered

| گزینه | چرا انتخاب نشد |
|---|---|
| Validator سفارشی (SPI) برای یکتا بودن Attribute کد ملی | Extension جاوا روی Keycloak -- بزرگ‌تر، حساس‌تر، و نگهداری در هر ارتقای Keycloak؛ در حالی که یکتایی نام کاربری از قبل داخلی است. |
| نگه داشتن Attribute و بررسی یکتایی در Backend/سایت بلیط | جلوی ساخت حساب تکراری را نمی‌گیرد؛ هر مصرف‌کننده باید جدا تداخل را مدیریت کند و کاربر در همان حالت خطا می‌ماند. |
| اجازه‌ی چند حساب و انتخاب حساب در سایت بلیط | هم پیچیده‌تر و هم خلاف «یک هویت مرکزی» (ADR-0003). |

## Consequences

- ورود با **کد ملی + گذرواژه** (ورود با ایمیل در Realm خاموش است).
- حساب‌های کارکنان/ادمین هم در همین Realm هستند، پس نام کاربری آن‌ها هم باید کد ملی باشد.
- فقط **فرمت** (۱۰ رقم) بررسی می‌شود، نه رقم کنترل کد ملی و نه مالکیت آن. اگر کسی زودتر با کد ملی
  دیگری ثبت‌نام کند، صاحب واقعی نمی‌تواند حساب بسازد و باید از پشتیبانی بخواهد (بررسی هویت، سپس حذف
  یا تغییر نام حساب مزاحم). آن حساب به حساب موجود در سایت بلیط هم نمی‌رسد، چون اتصال فقط با کد
  یک‌بارمصرف به شماره‌ی ثبت‌شده‌ی سایت انجام می‌شود (ADR-0023).
- **Realmی که از قبل کاربر دارد** باید مهاجرت کند: نام کاربری هر کاربر ← کد ملی‌اش (Admin، با روشن کردن
  موقت `editUsernameAllowed`)؛ از حساب‌های تکراری یکی بماند و اگر ردیف `users.app_user` مال حساب حذف‌شده
  است، `keycloak_subject` آن به حساب باقی‌مانده منتقل شود (وگرنه JIT آن حساب با خطای یکتایی کد ملی
  شکست می‌خورد). کاربری که نام کاربری‌اش کد ملی نیست، Claim `national_code` نامعتبر می‌گیرد.
- Production هنوز کاربری ندارد (Keycloak عمومی Deploy نشده)؛ Import تازه پروفایل را کامل می‌آورد.
- تأیید: توکن نمونه‌ی `mobile-app` و `django-ticketing` هر دو `national_code` = نام کاربری؛ ثبت‌نام تکراری
  و نام کاربری غیر ۱۰ رقمی رد شد؛ برچسب صفحه‌ی ورود «کد ملی»؛ Import تازه‌ی `sepahan-realm.json` روی
  Keycloak 26.7.1 همان پروفایل را ساخت؛ `fix-user-profile.sh` یک Realm قدیمی را به همین پروفایل رساند؛
  و «ورود با Fan ID» سایت بلیط با یک کاربر آزمایشی end-to-end (بار اول کد یک‌بارمصرف، بار دوم بدون کد).
